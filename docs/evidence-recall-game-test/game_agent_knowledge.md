# 游戏销量分析智能体知识库

> 用途：供 `EvidenceRecallNode` 做游戏销量、制作预算、营销预算、类型、平台、IP、评分和预测类问题的证据召回。数据库中的 40 款游戏均为虚构样本；本文中的阈值与公式若标注为“本项目口径”，只对测试库有效。

## AK-01 数据集范围、单位与边界

证据标识：AK-01。分析库由 `games`、`game_types`、`game_platforms` 三张表构成。`games` 是一款游戏一行的主表；类型与平台需要通过外键连接字典表。`actual_sales` 的单位是万份，`dev_budget`、`marketing_budget`、`total_investment`、`revenue` 的单位是万元，`price` 的单位是元/份，`review_score` 是 0—10 分。由于“元/份 × 万份 = 万元”，所以 `price * actual_sales` 与 `revenue` 的量纲一致。数据只记录 2019—2024 年间 40 款虚构游戏的累计表现，不含月度销量、国家地区、渠道、折扣、退款、DLC、内购、活跃用户和实时运营数据。面对“上个月销量”“某地区收入”“留存率”等问题，应明确当前 schema 不支持，不能编造答案。AK-01 结束。

## AK-02 游戏类型、子类型与标签

证据标识：AK-02。游戏类型（genre）描述核心玩法范式，本库用十个互斥的粗粒度主类型：角色扮演RPG、动作、策略、射击、模拟经营、休闲益智、体育竞技、冒险解谜、竞速、生存恐怖。现实游戏可能同时属于动作 RPG、策略 RPG、动作冒险等多个子类型，但本库每款游戏只有一个 `type_id`，因此按类型汇总时只能使用这一个主类型，不应把名称或题材自行拆成多标签。Steamworks 将标签区分为主类型、具体类型或子类型、视觉属性、主题与氛围、玩法特征等，并指出更具体的标签有助于描述和发现游戏；这说明“类型”与“标签”并非完全等价。若用户问“恐怖游戏”，本库应映射到“生存恐怖”；问“经营类”映射到“模拟经营”；问“RPG”映射到“角色扮演RPG”。AK-02 结束。

## AK-03 平台差异与跨平台比较

证据标识：AK-03。本库的平台为 PC、手机端、PlayStation、Xbox、Switch、VR，并且一款游戏只记录一个“主要发行平台”。平台会同时影响常见售价、受众规模、购买习惯和内容形态，因此跨平台只比较销量容易误导：低价手机游戏可能份数很高但单份收入低，主机游戏可能份数较少但售价和收入更高。公平比较至少应同时展示样本数、平均或中位销量、平均或中位收入、销量加权售价，并在可能时按类型、发行年份、IP 状态分层。本库不能回答同一作品在不同平台分别卖了多少，也不能把 `platform_id` 当成多平台数组。看到“全平台”一词时，只能解释为汇总本库所有主要平台记录，而不是现实中的跨平台总销量。AK-03 结束。

## AK-04 定价、商业模式与收入解释

证据标识：AK-04。本库把 `price` 视为单次买断售价，并用 `revenue = price × actual_sales` 得到简化总收入。现实游戏商业模式还可能包括 DLC、游戏内购、订阅和免费游玩等，Steamworks 官方定价文档也明确列出完整游戏单次购买、DLC、微交易和订阅等多种模式；这些收入来源没有进入本库。因此本库的 `revenue` 既不是净流水，也不是平台结算收入，更不是会计利润。跨作品计算平均售价时，`AVG(price)` 回答的是“游戏标价的简单平均”，而 `SUM(revenue)/SUM(actual_sales)` 回答的是“按销量加权的平均每份收入”，两者不能混用。分析低价高销量与高价低销量时，应并列报告销量、售价和收入，避免把销量冠军直接称为收入冠军。AK-04 结束。

## AK-05 制作预算、营销预算和回本口径

证据标识：AK-05。`dev_budget` 表示开发资金投入，`marketing_budget` 表示营销资金投入，`total_investment` 等于二者之和，单位均为万元。开发预算可作为内容生产投入的代理，营销预算可作为发行推广投入的代理，但表中没有授权费、渠道分成、税费、退款、服务器和长期运营成本。因而本项目的“回本”仅定义为 `revenue >= total_investment`，“回本金额差”为 `revenue - total_investment`，“简化 ROI”为 `(revenue-total_investment)/total_investment`。真实业务决策不得直接沿用这个粗略口径。预算效率比率容易被售价、平台、类型和 IP 混杂；做归因时先给描述性结果，再用同类型同平台同年份的可比组复核。遇到投入为零的分母必须排除或返回不可计算。AK-05 结束。

## AK-06 IP、系列作与原创游戏

证据标识：AK-06。`is_ip=1` 表示知名 IP 或续作，`is_ip=0` 表示原创或非知名 IP。本库把“IP”和“续作”合并为一个二元标志，无法进一步区分授权改编、系列续作、重制版或衍生作。比较 IP 与非 IP 时必须同时报告两组样本量、销量指标和收入指标；因为 IP 游戏可能集中在高售价主机平台或高预算类型，直接均值差不等于 IP 带来的因果提升。更稳妥的描述是“本样本中 IP 组与非 IP 组存在某种相关差异”。如需更接近同类对照，应在相同类型和平台内比较，或在建模中控制预算、价格、评分、年份等变量。不要依据名字猜测 IP 状态，唯一依据是 `games.is_ip`。AK-06 结束。

## AK-07 玩家评分与销量关系

证据标识：AK-07。`review_score` 是 0—10 的玩家综合评分。本项目默认将 8.5 分及以上标为“高评分”，但它只是为了复现实验而制定的阈值。评分与销量可能双向关联：口碑可能促进后续销售，销量更大的游戏也可能吸引更多不同偏好的玩家参与评分；同时平台、价格、IP、预算、类型和发行年份都是潜在混杂因素。因此“高评分游戏平均销量更高吗”应被处理为分组描述问题，不应把结果表述成“提高评分必然增加销量”。建议同时报告两组样本量、平均值、中位数和分布；样本较小时注明不确定性。预测新游戏时，如果发行前并不知道最终玩家评分，就不能把最终 `review_score` 当成可用的上线前特征。AK-07 结束。

## AK-08 营销投入、开发投入与边际效应

证据标识：AK-08。营销销量效率 `actual_sales/marketing_budget`、开发收入效率 `revenue/dev_budget` 和总投入 ROI 都是比率指标。高比率可能来自小分母，不能自动说明项目绝对表现更好。预算与销量之间也可能存在反向选择：发行方往往给预期更高的项目更多预算，所以正相关不等于预算导致销量增长。分析投入效果时应先画散点或分预算档位汇总，再按平台、类型、IP 和年份分层；报告相关系数时用“相关”而非“贡献”或“提升”。若要建立预测模型，建议对投入和销量检查偏态与极端值，采用交叉验证，并与简单的同类中位数基线比较。只有随机实验或充分的因果识别设计才能支持因果结论，本库不具备这种条件。AK-08 结束。

## AK-09 可比组、聚合与样本量规则

证据标识：AK-09。所有组间比较应先定义可比组。推荐优先级是：相同主要平台、相同主类型、相近发行年份，再视问题控制 IP、售价与投入档位。每个聚合结果必须保留 `COUNT(*)`，因为本库某些类型或平台只有很少样本；例如 VR 仅有一款游戏，不能把单条记录的表现称为稳定的平台规律。平均值对极端高销量手机游戏很敏感，条件允许时应同时给 `AVG`、`MIN`、`MAX`，并在报告层补充中位数。计算占比时，分子和分母必须使用同一过滤范围。排名应在过滤和聚合完成后执行，并使用稳定的并列排序。若查询要求现实行业结论，应提醒这 40 条虚构样本不具外推性。AK-09 结束。

## AK-10 异常值与“销量冠军不等于收入冠军”

证据标识：AK-10。手机端低价作品在本库中形成显著的“低价、高销量、相对低收入”群体，所以极高销量并不一定意味着极高收入。异常值检查应分别针对 `actual_sales`、`revenue`、`price` 和预算执行，不能只按单一指标删除记录。若某款游戏销量远高于同组，但字段值与库内规则一致，应把它作为真实的合成样本保留，并在均值解释中说明影响；只有发现单位错误、重复行或不可能值时才做数据清洗。回答“表现最好”时必须先澄清或显式选择指标：销量最好按 `actual_sales`，收入最好按 `revenue`，投入回报最好按简化 ROI。不要把三个榜单混成一个主观总榜。AK-10 结束。

## AK-11 销量预测的特征、泄漏与时间边界

证据标识：AK-11。销量预测目标是 `actual_sales`。上线前可合理使用的候选特征包括类型、平台、开发预算、营销预算、团队规模、开发周期、是否 IP、计划售价和发行年份。`revenue` 由售价与实际销量计算，预测销量时使用它会产生目标泄漏；最终玩家评分通常也是发行后才知道的变量，若任务是上线前预测，应排除最终评分或明确改成“发行后更新预测”。训练与验证最好按发行年份做时间切分，避免用未来作品预测过去；40 条样本很小，模型应保持简单，并报告交叉验证误差与基线误差。分类字段需要编码，数值字段需检查量纲和极端值。输出应是区间或带不确定性的估计，而不是伪精确单点。AK-11 结束。

## AK-12 标准预测分析流程

证据标识：AK-12。预测下一款游戏销量时按以下流程：第一，确认预测时点和可用字段，排除 `revenue` 与任何发行后才产生的特征；第二，检查数据量、缺失值、重复值和单位；第三，用类型、平台、IP、预算档位建立同类样本基线，至少给出同类中位数或均值；第四，选择简单可解释模型并用时间切分或交叉验证评估；第五，比较模型与基线的 MAE 或 RMSE；第六，对开发预算、营销预算、售价等关键输入做情景分析；第七，输出预测区间、主要驱动因素、样本局限和不可外推声明。如果目标新游戏的类型、平台、预算或 IP 状态缺失，应先请求最小必要信息，而不是擅自补值。40 条虚构记录适合验证工作流，不适合真实商业预测。AK-12 结束。

## AK-13 SQL 连接与常见查询模式

证据标识：AK-13。按类型查询使用 `games g JOIN game_types t ON g.type_id=t.id`；按平台查询使用 `games g JOIN game_platforms p ON g.platform_id=p.id`；同时按类型和平台分析时连接三表。事实字段来自 `games`，类型名用 `t.name`，平台名用 `p.name`。聚合查询选择了类型名或平台名时必须放入 `GROUP BY`。年度筛选使用 `g.release_year`，不是 `created_at`；后者只是入库时间。销量 TopN 对 `g.actual_sales` 排序，收入 TopN 对 `g.revenue` 排序，ROI 排名先计算表达式再排序。除非用户明确要求，不应把字典 ID 展示为最终业务结果。为避免整数或零除问题，可使用 `NULLIF(denominator,0)`，百分比乘以 `100.0`。AK-13 结束。

## AK-14 输出规范与结论强度

证据标识：AK-14。数据问答至少包含：所用口径、过滤范围、样本量、结果表和一句局限说明。金额保留两位小数并标“万元”，销量保留两位小数并标“万份”，百分比保留两位小数。若问题使用“影响”“驱动”“导致”等因果词，而当前分析只是观察数据，应将结论降级为“相关”“同组差异”或“描述性关联”。若结果违反先验，例如高评分组平均销量反而更低，应忠实报告，并检查平台和售价构成，不要为了迎合行业常识改写结果。所有现实行业资料只提供解释框架，数据库查询结果必须来自当前表。AK-14 结束。

## AK-15 活跃用户、留存率与游戏时长

证据标识：AK-15。活跃用户通常需要用户标识、登录或游戏会话时间等事件数据；日活跃用户 DAU、月活跃用户 MAU、次日留存、七日留存、游戏时长和流失率都不能由当前三张表计算。本库只有每款游戏的累计销量，购买并不等于活跃，售出一份也不等于一个唯一玩家。若用户询问“哪类游戏留存最好”“2024 年月活是多少”“销量用户中还有多少人在玩”，应返回当前 schema 缺少用户级与时间序列行为数据，并建议新增 `player_sessions(game_id,user_id,session_start,duration)` 或按日聚合的活跃表。不得使用 `actual_sales` 冒充活跃用户，也不得用 `created_at` 冒充玩家活动日期。AK-15 结束。

## AK-16 愿望单、曝光与购买转化漏斗

证据标识：AK-16。营销漏斗可包含商店曝光、页面访问、愿望单新增、试玩、购买和退款等环节；每一步都需要独立事件或汇总字段。Steamworks 的愿望单报表会区分新增、购买和删除，并可按地区或愿望单加入月份观察，但当前测试库没有曝光、访问、愿望单或购买事件，所以不能计算曝光点击率、愿望单转化率、商店页转化率和获客成本。`marketing_budget` 只有投入，没有漏斗分母；`actual_sales/marketing_budget` 是粗略效率比，不是转化率。若要支持此类分析，应增加带 `game_id`、日期、渠道和漏斗阶段的营销事实表，并明确用户去重和归因窗口。AK-16 结束。

## AK-17 DLC、内购、订阅与 ARPU

证据标识：AK-17。现实游戏收入可能来自基础游戏、DLC、装饰品或道具内购、虚拟货币、战斗通行证和订阅。Steamworks 也将游戏内购买称为 microtransactions 或 IAP，并提供交易、退款与状态查询能力。当前测试库把所有产品简化为按 `price` 买断，并只保存 `price × actual_sales` 的收入，没有玩家付费事件、DLC、订阅或内购字段。因此不能计算 ARPU、ARPPU、付费率、LTV、DLC 附着率或内购流水，也不能把低价手机端样本当作免费游戏。若用户问这些指标，应说明缺失字段，而不是从 `revenue/actual_sales` 推导 ARPU；该比值在本库只是每份售出的平均收入。AK-17 结束。

## AK-18 区域定价、币种与本地化

证据标识：AK-18。游戏平台可能按地区使用不同币种和不同价格，Steamworks 定价文档也描述了多币种与地区定价工具。当前 `price` 只有一个人民币元口径的单值，数据库没有国家、地区、币种、汇率、税制、本地化语言或区域销量。因此不能回答“中国区和欧美区哪个收入高”“汇率变化影响多少”“本地化是否提升销量”等问题。跨游戏价格比较只能把 `price` 当作本测试库统一口径下的买断售价。若要支持区域分析，需要订单或地区销售事实表，至少包含 `game_id`、region、currency、local_price、exchange_rate、units、gross_revenue、date`，并统一汇率日期与含税口径。AK-18 结束。

## AK-19 折扣、促销与销量时间序列

证据标识：AK-19。折扣深度、促销曝光和活动窗口可能改变短期销量，但当前库只有单一 `price` 与累计 `actual_sales`，没有原价、成交价、折扣百分比、活动名称、日销量或周销量。Steamworks 官方文档把折扣视为扩大受众和延长产品生命周期的工具，同时强调应结合具体产品与社群理解；这类通用经验不能替代本库中不存在的促销数据。当前无法回答“打七折销量提升多少”“季节促销 ROI”“首发折扣转化率”。要分析促销，应新增按游戏、日期、地区或渠道记录的价格和销量表，并以活动前后可比窗口或更严格的对照设计评估。AK-19 结束。

## AK-20 同时在线、峰值并发与服务器指标

证据标识：AK-20。同时在线人数 CCU、峰值同时在线 PCCU、并发峰值时间、服务器容量和匹配等待时间是运营或遥测指标，需要带时间戳的在线会话或监控数据。本测试库的 `team_size` 是开发团队人数，与玩家并发无关；`actual_sales` 是累计售出份数，也不能换算为同时在线。面对“哪款游戏峰值在线最高”“销量能支撑多少服务器”“PC 平台并发趋势”等问题，应判为当前数据库不可回答。若扩充数据，可增加 `concurrency_metrics(game_id, observed_at, ccu, server_region)` 并明确采样频率、时区和峰值聚合规则。AK-20 结束。

## AK-21 退款、渠道分成、净收入与利润

证据标识：AK-21。毛流水、平台结算收入、净收入和利润必须区分。本库 `revenue` 只是售价乘累计销量的简化总收入，没有退款金额、折扣、税费、支付手续费、渠道或平台分成、发行商分成、版权费与运营成本，所以无法计算真实净收入、毛利、营业利润或净利润。Steamworks 的微交易实现资料明确存在退款和交易状态，这进一步说明现实收入核算不能忽略逆向交易。若用户要求“扣除 30% 平台分成后的利润”，除非用户明确把 30% 作为假设，否则不能擅自套用固定分成比例。可以提供参数化情景公式，但必须把假设与数据库事实分开标注。AK-21 结束。

## AK-22 年龄分级、内容描述与受众适配

证据标识：AK-22。年龄分级与玩家评分不是同一概念。ESRB 分级用于提供游戏或应用内容信息，并包含分级类别、内容描述和互动元素；`review_score` 则是本库的玩家综合评分。当前数据库没有 ESRB、PEGI、防沉迷、内容描述、目标年龄或受众标签，因此不能按年龄分级统计销量，也不能从“生存恐怖”类型自动推断具体分级。若要分析受众适配，应增加独立分级与内容标签字段，并保留分级制度与地区，因为不同市场采用的体系可能不同。任何时候都不能用 0—10 的 `review_score` 代替年龄等级。AK-22 结束。

## AK-23 版本更新、赛季与长线运营

证据标识：AK-23。版本更新、赛季、活动、内容投放与运营节奏可能影响活跃、付费和销量，但当前库只保留游戏级静态或累计字段，没有版本号、更新日期、赛季、活动事件或按时间销量。`release_year` 只表示发行年份，不能代表每次更新，也无法识别早期访问、正式版或重大资料片。用户询问“更新后销量是否提升”“哪个赛季收入最高”“长线运营效果”时，应说明数据粒度不足。所需扩展可包含 `game_updates`、`liveops_events` 与按日销售表，并用事件前后窗口、同期对照和季节性校正进行分析。AK-23 结束。

## AK-24 发行日期、季节性与生命周期

证据标识：AK-24。本库只有整数年份 `release_year`，没有月份、日期、上市周数或销量曲线，因此可以做按年分组，但不能做季度、月份、首周、首月、长尾或节假日季节性分析。累计销量还受上市时长影响：较早发行的游戏可能拥有更长累积窗口，直接与新作比较会混入生命周期差异。若问题要求近三年，本项目按数据最大年份向前包含三个自然年，但这不是滚动 36 个月。要评估生命周期，需要 `release_date` 和按日或按月的增量销量；汇总时必须区分期间新增销量与截至某日累计销量。AK-24 结束。

## AK-25 开发商、发行商与团队归属

证据标识：AK-25。游戏可能由开发商制作、发行商发行，并可能涉及联合开发、外包、授权方或不同地区发行主体。当前库只有 `team_size`，没有开发商、发行商、工作室、地区、所有权或人员构成。`team_size` 只是人数规模，不能推断开发效率、团队经验或公司能力，也不能把游戏名称当作厂商名称。用户问“哪个发行商收入最高”“某工作室最擅长什么类型”“国内外团队差异”时，当前 schema 不支持。若新增组织维度，应建立开发商与发行商字典及多对多关系，并明确收入归属口径。AK-25 结束。

## AK-26 评论数量、评分置信度与口碑文本

证据标识：AK-26。相同的 `review_score` 在 10 条评论与 10 万条评论下置信度完全不同，但当前表没有评论数量、正负面比例、评论时间、语言或文本。因此只能使用评分点估计，不能计算评分置信区间、近期口碑趋势、评论情感或“好评如潮”等平台标签。也不能从销量反推评论数。若要更稳健地比较评分，应新增 `review_count`、`positive_count` 与带时间戳的评论汇总，并考虑小样本收缩或贝叶斯平均。用户要求读取玩家具体反馈时，应说明需要评论明细或外部数据源，不能把游戏名称和分数扩写成虚构评论。AK-26 结束。
